# proc-reaper — уборка зависших процессов Windows

Решает конкретную болезнь: `npm run dev` на Windows порождает цепочку
`node (npm) → cmd.exe → node (vite)` плюс `conhost`. Когда запустившая оболочка
умирает, дерево **не умирает вместе с ней** — в Windows нет process group kill.
Каждый такой запуск оставляет 3–4 вечных процесса.

Как это выглядело до установки: 1330 процессов, из них 420 `node`, 208 `cmd`,
226 `conhost`; 193 живых dev-сервера одного проекта на портах 9555–9747,
214 тысяч хендлов, 4.7 ГБ RAM.

## Четыре уровня защиты

| Уровень | Файл | Что делает |
|---|---|---|
| Уборщик | `reap.ps1` | Находит и убивает сирот и дубликаты |
| Автозапуск | Задача `ProcReaper` | Гоняет уборщик раз в 4 часа (03:50), невидимо |
| Конец сессии | `hooks/proc-reap-session.mjs` | Чистит за сессией Claude Code |
| Профилактика | `dev-run.ps1` | Job Object: ОС сама убивает дерево |

## reap.ps1 — уборщик

По умолчанию **ничего не убивает**, только печатает список.

```powershell
.\reap.ps1                 # dry-run, показать кандидатов
.\reap.ps1 -Force          # убить
.\reap.ps1 -Force -Json    # машинный вывод, для хуков
.\reap.ps1 -Aggressive     # всё, кроме чёрного списка (по умолчанию выключено)
```

Процесс должен пройти **все** защиты, а затем совпасть с **любым** правилом.

**Защиты — эти не трогаются никогда:**

- имя в `Blacklist` (ядро ОС, браузеры, редакторы) или служба в сессии 0;
- сам уборщик и вся цепочка его родителей;
- возраст меньше `MinAgeMinutes` (10 мин);
- есть видимое окно — значит, за ним кто-то работает;
- **всё живое поддерево** под VS Code, Claude, Terminal, explorer, Docker
  (`ProtectDescendantsOf`) — dev-сервер, висящий на открытом окне редактора,
  используется, а не брошен.

**Правила отстрела:**

- **Сирота** — родителя нет, либо родитель создан *позже* ребёнка (PID
  переиспользован, значит настоящий родитель мёртв).
- **Дубликат** — от `DupThreshold` (3) процессов с одинаковой командной строкой:
  оставить `KeepNewest` (1) свежайших, остальные убить.
- **Осиротевший агент** (`ReapWhenOrphaned`) — исключение из чёрного списка, см. ниже.
- **Простаивающий агент** (`IdleAgents`) — живой `claude.exe` под живым окном,
  которым ≥8 ч никто не пользовался, см. ниже.
- **Потомок** — живые дети убитого процесса уходят следом.

## Почему `claude.exe` висит после закрытия чата

Расширение VS Code запускает **`claude.exe` на каждую сессию** (наблюдалось
шесть агентов под одним окном). Живёт он до закрытия окна: закрыть вкладку чата
недостаточно, процесс остаётся вместе со своими MCP-серверами, их `node`,
`docker run` и `conhost`. Это устройство расширения; окончательно убирается
закрытием окна, накопившихся снимает правило `idle-agent` (см. ниже).

Утечка возможна одна: если VS Code **падает**, а не закрывается штатно. Тогда
`claude.exe` и всё его поддерево остаются навсегда — имя `claude` стоит и в
`Blacklist`, и в `ProtectDescendantsOf`, то есть было неприкосновенно вообще для
любого правила.

Правило `ReapWhenOrphaned` — это исключение, и оно срабатывает **только когда
родитель мёртв**. Живой агент не трогается никогда: у него живой `Code.exe` в
родителях. Отсрочка `OrphanGraceMinutes` (15 мин) больше общей `MinAgeMinutes`:
агент, запущенный отдельно и намеренно в фоне, тоже не имеет живого родителя, и
ему надо дать доработать.

Порядок в коде важен: список осиротевших агентов считается **до** построения
защищённых поддеревьев, иначе мёртвый агент, будучи сам корнем защиты, укрыл бы
собственных детей от уборки.

Проверено: подставной осиротевший процесс с именем из чёрного списка попадает в
план как `orphan-agent`; при этом ни один живой `claude.exe`, ни сам уборщик, ни
его предки в план не попадают.

## Простаивающие агенты — `idle-agent`

Практика показала: агенты копятся не только при падении VS Code. Расширение
оставляет `claude.exe` **на каждую сессию**, и под давно открытыми окнами
скапливаются агенты вчерашних чатов — каждый со своим комплектом MCP-серверов
и tsserver на 1–3.5 ГБ. Для уборщика всё это «живое поддерево живого окна».

Правило `idle-agent` снимает такой агент вместе со всем поддеревом по двум
триггерам; обоим нужна история почасовых замеров CPU
(`%LOCALAPPDATA%\proc-reaper\agent-activity.json`, первые срабатывания —
через `IdleAgentHours` после включения):

- **idle** — собственный CPU агента вырос ≤ `IdleAgentCpuBudgetSec` (300 с)
  за окно `IdleAgentHours` (8 ч). Замерено на рабочей машине разработчика: брошенные агенты
  дрейфуют 16–35 с/час (максимум ~280 с за 8 ч), используемые — больше.
  Именно **собственный** CPU, не поддерева: MCP-поллеры жгут 40–370 с/час
  в деревьях, которых никто не трогает, а запись на диск оказалась
  перевёрнутым сигналом (застойные агенты спамят логи по 50–230 КБ/мин,
  активный пишет почти ничего).
- **stale** — агент старше `IdleAgentMaxAgeHours` (24 ч) **и** не держит
  установленного не-loopback TCP-соединения. Ловит аномального агента,
  крутящего фоновый цикл мимо CPU-бюджета; проверка соединения не даёт
  убить зависший, но ещё подключённый к API стрим.

Замеченное: агент, чей чат давно закрыт, может держать соединение к API
сутками — он переживёт оба триггера, пока соединение не отвалится. Это
осознанно: лучше день лишнего процесса, чем убитый на середине запрос.

Вместе с агентом умирает и dev-сервер, запущенный из той сессии. Тоже
осознанно: стенд, к которому 8 часов никто не прикасался, — мусор;
перезапуск — одна команда. Стенд, нужный дольше, запускайте не из сессии
Claude, а через `dev-run` или свой терминал.

## MCP-серверы — где реально копятся процессы

Каждый агент поднимает MCP-серверы своего проекта из `.mcp.json` **сразу при
старте**, использует их сессия или нет. Отсюда `node`, `npx`, `docker run` и
`conhost` пачками. Сокращать нужно `.mcp.json` проекта, а не убивать процессы.

Предохранитель `MaxKillsPerRun` (1000); превышение — предупреждение в консоль,
не тихое обрезание. Лог: `%LOCALAPPDATA%\proc-reaper\reap.log`.

В логе `cascaded` — процессы, умершие сами: убийство `vite` заставляет
родительский `cmd /c` завершиться, а тот отпускает `conhost`. Это успех, не сбой.

## reap.config.json

Правится без трогания кода: пороги, белый и чёрный списки, `Protect` (имена или
конкретные PID, неприкосновенные), `ProtectDescendantsOf`.

Белый список широкий: node, npm/pnpm/yarn/bun, vite, esbuild, webpack, tsc,
jest/vitest/cypress/playwright, драйверы браузеров, python, java, dotnet, go,
ruby, php, cmd, conhost, powershell, bash, git — 85 имён.

**Logitech G HUB выведен из всех правил.** `lghub`, `lghub_agent`,
`lghub_system_tray`, `lghub_updater`, `logi_lamparray_service` и родня — в чёрном
списке: ни как цель, ни как дубликат, ни как потомок убитого. Уборщик их не
чистит и не перезапускает. Причина общая для всего, что обслуживает устройства
ввода: убийство такого помощника заново поднимает HID-стек, и мышь замирает на
несколько секунд.

## Задача планировщика

```powershell
.\install-task.ps1              # поставить, интервал 240 минут, старт 03:50
.\install-task.ps1 -Minutes 60
.\install-task.ps1 -StartTime 02:15
.\install-task.ps1 -Uninstall
```

**Почему 4 часа, а не час.** Один прогон убивает 5–20 деревьев процессов разом и
на ~15 секунд разгоняет запись в реестр — ежечасно это ощущается как
периодическое подтормаживание рабочего стола. Мусор, который он собирает, не
срочный. Уборщик наблюдателей VS Code разнесён по времени (00:40), чтобы два тяжёлых
прохода не совпадали.

Сделана через `schtasks.exe`, а не `Register-ScheduledTask`: второй
сериализует бесконечное повторение как `P99999999DT23H59M59S`, и планировщик
Windows такое отвергает.

**Полная невидимость.** Задача запускает не `powershell.exe` напрямую, а
`run-hidden.vbs`. Причина: `powershell -WindowStyle Hidden` всё равно создаёт
окно консоли и прячет его мгновением позже — видно это как вспышка, и этого
хватает, чтобы увести фокус из полноэкранной игры. `WScript.Shell.Run` со стилем окна `0`
не создаёт окно вообще. Проверено: за время работы задачи не появляется ни
одного нового `conhost`.

Сам скрипт при старте понижает себе приоритет до `BelowNormal` — фоновый
уборщик не должен соперничать с тем, что происходит на переднем плане. Не
`Idle`: под нагрузкой от игры такой процесс может не получить времени вовсе.

## dev-run.ps1 — лечение причины

Запускает команду внутри Windows Job Object с флагом
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Обёртка сначала помещает **себя** в job —
членство наследуется, поэтому все потомки попадают в job автоматически, без гонки.
Когда обёртка исчезает (обычный выход, Ctrl+C, taskkill, падение), ОС убивает
всех членов job.

```powershell
dev-run npm run dev
dev-run pnpm --filter @my-app/web dev
```

Проверено: dev-сервер поднялся на 9555, убита **только обёртка** — дерево
умерло целиком, порт освобождён.

Чтобы вызывалось просто как `dev-run`, добавьте
`%USERPROFILE%\.claude\tools\proc-reaper` в `PATH` — там лежит `dev-run.cmd`.

## Отдельно: strictPort

В `vite.config.ts` проекта без `strictPort: true` повторный запуск не падает с
«порт занят», а молча берёт следующий свободный. Именно это позволило накопить
193 сервера. Ставьте `strictPort: true` в каждом проекте — тогда лишний запуск
сразу виден как ошибка.
