# vscode-watcher-reaper — отстрел залипших наблюдателей VS Code

Лечит конкретную болезнь: процесс `file-watcher` (по одному на каждое окно
VS Code) срывается в холостой спин-луч и держит **целое ядро** до перезапуска.
Апстрим-баг [microsoft/vscode#303702](https://github.com/microsoft/vscode/issues/303702)
в нативном `@parcel/watcher`, открыт.

Как это выглядело 16.08.2026, VS Code 1.133.0, четыре окна: четыре вотчера по
100% ядра каждый — **~12% всего 32-поточного процессора** в полном простое.

## Почему это спин-луч, а не работа

| Показатель | Залипший | Здоровый |
|---|---|---|
| CPU | 100% одного ядра непрерывно | 0,3% |
| «Прочие» I/O-операции | **226 000/сек** | 31/сек |
| Прочитано и записано байт | **0** | ~240 Б/сек |
| Время в режиме ядра | 84% | — |

Разрыв в четыре порядка — поэтому пороги можно ставить с огромным запасом и не
рисковать зацепить занятый процесс.

**Триггер** по апстрим-треду — массовое удаление файлов, находящихся под
наблюдением. Здесь ему предшествовали `go clean -cache` и `npm cache clean --force`.

## `files.watcherExclude` тут не поможет

Исключения режут **объём** наблюдения, а спин от объёма не зависит: воркспейс из
158 папок горел ровно так же, как воркспейс из 23 832 папок, и памяти оба вотчера ели одинаково — по 136 МБ. Исключения там к
тому же уже были настроены.

Отключить вотчер совсем нельзя, и не нужно: через него работают подхват правок,
сделанных мимо редактора (а Claude Code правит файлы именно так), обновление
проводника, git-декорации и реакция tsserver на внешние изменения.

## Как отличается залипший от рабочего

Имя процесса и командная строка у `file-watcher`, `extension-host`, `pty-host` и
`shared-process` **одинаковые** (`--type=utility --utility-sub-type=node.mojom.NodeService`),
поэтому цель определяется по подписи. Убивается только при совпадении всех
четырёх условий разом:

- ≥ `MinCorePct` (80%) одного ядра **непрерывно** всё окно замера, а не всплеск;
- ≥ `MinOtherOpsPerSec` (50 000) «прочих» I/O-операций в секунду;
- ≤ `MaxBytesPerSec` (256 КБ/с) реального трафика — спин-луч байты не двигает;
- ≥ `MinKernelPct` (60%) времени в режиме ядра — там и сидит холостой системный вызов.

Extension host, tsserver и pty-host под это не попадают: они либо гоняют байты,
либо работают в user mode. Проверено на живой системе: с боевыми порогами — ноль
ложных срабатываний, с обнулёнными видит все 12 node-процессов.

Убитый вотчер VS Code поднимает сам, окна и несохранённое не трогаются.

## Запуск

```powershell
.\watcher-reap.ps1                 # dry-run, только показать кандидатов
.\watcher-reap.ps1 -Force          # убить
.\watcher-reap.ps1 -Force -Quiet   # для задачи: писать только в лог
```

Лог: `%LOCALAPPDATA%\vscode-watcher-reaper\watcher-reap.log`. Каждый прогон
оставляет одну строку даже когда чисто — иначе по логу не отличить «нечего
убивать» от «задача перестала запускаться».

## Задача планировщика

```powershell
.\install-task.ps1              # поставить, интервал 120 минут, старт 00:40
.\install-task.ps1 -Minutes 240
.\install-task.ps1 -Uninstall
```

**Почему 2 часа, а не 5 минут.** Сама проверка дешёвая, но каждый прогон
порождает `powershell.exe` и `conhost` — ровно тот мусор, ради которого заведён
`proc-reaper`. Плата за редкий интервал: вотчер, залипший сразу после прогона,
сожжёт ядро до следующего. Старт 00:40 разведён с `ProcReaper` (03:50) и
`ToolkitSync` (05:20), чтобы тяжёлые фоновые проходы не совпадали.

**Полная невидимость.** Задача запускает не `powershell.exe`, а `run-hidden.vbs`:
`powershell -WindowStyle Hidden` всё равно создаёт окно консоли и прячет его
мгновением позже — видно как вспышка, и этого хватает, чтобы увести фокус из
полноэкранной игры. `WScript.Shell.Run` со стилем окна `0` не создаёт окно вообще.
Проверено: прогон задачи не добавил ни одного нового `conhost`.

Сам скрипт при старте понижает себе приоритет до `BelowNormal`.

## Если залипло прямо сейчас

Ждать задачу не обязательно — `.\watcher-reap.ps1 -Force` отрабатывает за 8 секунд.
Руками то же самое: **Help → Open Process Explorer** → правый клик по
`file-watcher` → Kill. Имена процессов там же показывает `code --status`.
